Revisão rápida

Um arquivo editado duas vezes no VS Code, dois commits, e um reset --hard pra reaquecer — o mesmo fluxo da aula passada, de novo com as mãos no teclado.

recap-aula-04/
# cria o repositório .git nesta pasta
$ git init
# manda os arquivos pra área de preparação (staging)
$ git add .
# grava um snapshot permanente do que foi preparado
$ git commit -m "Cria anotacoes.txt..."
$ git add .
$ git commit -m "Adiciona segunda linha..."
# --oneline resume cada commit em uma linha só
$ git log --oneline
# desfaz o último commit, mesmo ele já tendo sido salvo
$ git reset --hard HEAD~1

Todo esse histórico, até agora, vive só nessa máquina. É esse ponto que a aula de hoje resolve.

"Deletados"? Vocês nunca chegaram a ter esses arquivos — e um único comando trouxe tudo de volta.

Só o que foi commitado mora dentro do .git — o que está no .gitignore nunca chega a existir ali, e por isso nunca volta.

HEAD e a branch: ponteiro pra ponteiro

es-aula-05/
# mostra pra qual branch o HEAD está apontando agora
$ cat .git/HEAD
ref: refs/heads/main
# mostra o hash do commit que a branch main aponta
$ cat .git/refs/heads/main
1878ee023677560b204d2427f3a3c900c1c0986b

HEAD não guarda um commit direto — aponta pra outro arquivo (a branch), que aponta pro commit.

Mesmo hash do topo do git log. Uma branch é só um arquivo de texto com um hash dentro.

Repositório: o lugar, não o conteúdo

Repositório, no sentido amplo da palavra, é só isso: um lugar onde algo fica guardado, armazenado — nem todo repositório é de código. Um repositório de arquivos, de dados, de peças — a palavra não é exclusiva do Git.

No universo do Git, o que se guarda dentro desse lugar é justamente o .git — o histórico completo de versões de um projeto (objects, refs, HEAD). Até aqui, o "lugar" onde esse .git está guardado é uma única pasta, numa única máquina.

# repositório local
o lugar: seu HD.
o que ele guarda: o .git.
# repositório no GitHub
o lugar: um servidor na internet.
o que ele guarda: o mesmo .git.

GitHub é um serviço de hospedagem — ele oferece o "lugar" na internet. O que fica guardado ali dentro é exatamente o .git, por isso clone, push e pull conseguem trafegar esse conteúdo entre sua máquina e o GitHub, do mesmo jeito que trafegariam entre duas máquinas quaisquer.

Criando o repositório no GitHub

  • Em github.com, clica no + (canto superior direito) → New repository
  • Dá um nome e escolhe Public ou Private
  • Não marca Add a README — o repo tem que nascer vazio
  • Confirma em Create repository

Na página do repo recém-criado: botão verde Code → aba SSH → copia a URL. É o que entra no próximo comando.

Chave SSH: gerando e cadastrando

A pública é o cadeado que vocês entregam pro GitHub guardar. A privada é a única chave que abre — e fica só com vocês, nunca sai da máquina.

~
# gera o par de chaves SSH (pública e privada)
$ ssh-keygen -t ed25519 -C "voce@email.com"
# mostra a chave pública, pra copiar
$ cat ~/.ssh/id_ed25519.pub
# testa se o GitHub reconhece a chave
$ ssh -T git@github.com
Hi usuario! You've successfully authenticated...
  • Clica na sua foto de perfil (canto superior direito) → Settings
  • No menu lateral, entra em SSH and GPG keys
  • Botão verde New SSH key
  • Em Title, dá um nome pra identificar essa máquina (ex: "meu notebook")
  • Em Key, cola o conteúdo copiado do id_ed25519.pub
  • Confirma em Add SSH key

Vendo essa mensagem, a autenticação já está pronta — o próximo git push não vai pedir senha nenhuma.

Cadastrando o remote

es-aula-05/
# cadastra o endereço remoto com o apelido "origin"
$ git remote add origin git@github.com:usuario/repo.git
# confirma que o endereço foi salvo no config
$ cat .git/config
[core] ...
[remote "origin"]
url = git@github.com:usuario/repo.git

git remote add não fez mágica de rede — só escreveu duas linhas num arquivo texto.

clone, push e pull

# baixar (1ª vez)
git clone <url>
# enviar
git push -u origin main
# receber
git pull

git clone é o comando de "primeira vez": baixa o repositório inteiro do GitHub (todo o .git) e já cria a pasta local, sem precisar de git init nem git remote add na mão.

Decompondo git push -u origin main: origin é o remote (pra onde vai), main é o branch (o que vai), e -u marca os dois como o padrão — só precisa na primeira vez. Depois disso, git push e git pull sozinhos já sabem pra onde ir.

clone é usado uma vez, quando o repositório local ainda não existe. push e pull são o dia a dia depois disso: flexão pra empurrar o que é seu pra fora, barra pra puxar o que tá lá fora pra perto de você.

troubleshooting

Cadê o .git no VS Code?

  • Ctrl + , abre as Settings
  • Buscar files.exclude
  • Desmarcar a entrada **/.git
{
  "files.exclude": {
    "**/.git": false
  }
}
